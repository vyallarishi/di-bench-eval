## What the benchmark promises

**The task.** Given a Python repository and one of its declared dependencies D, remove D: delete the declaration, change the code so it no longer needs D, and keep CI (the repository's own GitHub Actions workflow, replayed with `act`) passing. The benchmark is a set of (repository, dependency) pairs.

**The promise for each pair, in full:**
1. *Gold passes.* The repository's unmodified manifest passes CI in our harness, so a failure after removal is caused by the removal.
2. *Removal is detected.* With D removed and made unimportable from the repository's own code, CI fails, and the failure is caused by the repository's own use of D — not by some other installed package that happens to import D, not by a lock file going stale, not by a linter choking on a file we injected.
3. *Removal is winnable.* An agent (or a careful human) could edit the repository so that it no longer needs D and CI passes under the same harness. Nothing about the pair makes that impossible.
4. *Labels are right.* Each pair carries a tier (`indirect` / `strong` / `medium` / `hard`, from how many non-test files import D), a `verified_by` and `evidence` field, static footprint fields (`source_files`, `test_files`, `test_reachable`, `attribute_uses`), and a `phantom_predicted` flag. Each of these must be correct for the pair.
5. *Exclusions are right.* Every candidate pair that was dropped is listed in an `excluded.jsonl` with a reason. The reasons must be true, and nothing that should have been kept was dropped.
6. *The grader is sound.* The run-time mechanism that makes D unimportable (an "origin-scoped" import blocker in `scripts/gh/make_blocked.py`) must block imports made by the repository's code and tests, must not block imports made by third-party packages, must not be bypassable by cached modules, and must not itself cause failures.

## What to do

Work through every layer. For each, say what you checked, how many items, what you found, with instance ids. Do not sample where you can check everything by machine; sample only for checks that need reading.

**A. Rules audit.** Read `classify()` and every regex in `build_pool.py`. For each rule, construct or find a log that it would misclassify. Specifically test: (1) the frame-origin regexes against pytest-style, plain-Python, tox, nox and unittest tracebacks; (2) whether `names_of()` (which splits package names on `_`) can match the wrong module (e.g. a package `python_x` matching a missing module `python`); (3) whether `INSTALL_STEP` / `LINT_STEP` step-name matching can mislabel a step that both installs and tests; (4) the `test_failure_without_import_error` rule, which keeps a pair whenever CI failed with no import error — find pairs where that failure is actually flakiness, a network call, a timeout, or a lock file.

**B. Per-pair log audit.** Download the result artifacts and, for every pair in the pool, independently re-derive from the raw log: the first error, the frame that raised it, whether it names D, and the failing CI step. Compare with the pair's `evidence`. Report every disagreement. Then read by hand every pair in the weak classes (`test_failure_without_import_error`, `linter_step_failed`, the "footprint 0" pairs, and every pair whose only repository-origin frame is in a test file), plus a random 30 of the rest.

**C. Winnability audit.** For a stratified sample of at least 25 pairs across tiers and both subsets, open the repository and decide whether removing D is actually possible: where is D used, is it replaceable, would the tests have to change, does the CI config or a pytest plugin or Django `INSTALLED_APPS` reference D, is D a build-time requirement, does another declared dependency require D so that it stays installed regardless. For at least 5 `strong` pairs, actually write the removal, apply the scoped blocker, and run the repository's tests locally (or in Docker) to show the pair is winnable. Any pair you cannot see how to win is a finding.

**D. Blocker audit.** Read `BLOCKER` in `make_blocked.py`. Try to break it: imports from `exec`-ed strings, `__import__`, `importlib.import_module` with the name built at run time, `pkgutil`, entry points, `multiprocessing` spawn (does `sitecustomize` load in the child?), subprocess `python -c`, Cython/C-extension modules, namespace packages, a package whose import name differs from its distribution name, a repository that is pip-installed non-editable into site-packages, `pytest -p` plugins, a test that `del sys.modules[...]` and re-imports, a foreign package that imports D lazily after a repository import has been blocked. Check the `_Guard` proxy: attribute access, `isinstance` against classes from D, pickling, `inspect`, `importlib.reload`. Check `own_packages()` for mis-detection. Build small repositories to demonstrate each break you find; also check whether anything in the blocker could make CI fail for a reason other than the repository's use of D (formatters, type checkers, `--doctest-modules` collecting the injected files, coverage configs).

**E. Static features audit.** For 30 pairs, hand-count the files importing D and compare with `footprint_files`, `source_files`, `test_files`, `test_reachable`, `attribute_uses`. Check that import-name mapping (`footprint.import_names`) is right for every distinct package in the pool — list the mappings and flag any you doubt. Check the tier thresholds make sense and are applied consistently.

**F. Exclusions audit.** For every reason string in `excluded.jsonl`, read at least 5 examples and decide whether the reason is true. Look especially at "unwinnable or framework-loaded" (some are Django apps or pytest plugins the repository itself configures — were winnable pairs thrown away?), "undetermined", "install step failed" (is the install failure caused by our manifest edit?), "blind spot: CI passes" (should any have been caught — i.e. is the blocker failing to fire?).

**G. Manifest edit audit.** For 30 pairs, diff the mutant manifest against the gold manifest and confirm exactly one declaration was removed and nothing else changed (`predictions/<set>/python/<mutant_id>/patch.diff`). Run `scripts/gh/test_manifests.py --full`. Look for formats the parser silently mishandles: Poetry groups, PEP 735 dependency groups, `setup.py` with `install_requires=read_requirements()`, `requirements.txt` with `-c` constraints or nested `-r` includes, extras, environment markers that exclude the CI platform (a dependency marked `sys_platform == "win32"` is never installed on Linux, so "removing" it changes nothing — is any such pair in the pool?).

**H. Harness audit.** Determine whether a single CI run is a reliable oracle here: find any repository in the pool whose gold or mutant result flips between runs (compare gold runs where instances were evaluated twice), and any whose CI depends on network, time, or secrets. Check that "CI fails" is not "CI errored for harness reasons" (act image pull, disk, timeout 1200 s).

**I. Claim audit.** List every quantitative statement about the benchmark in `oracle-blindness/README.md`, `oracle-blindness/docs/*.md`, the paper source if present, and the memory note. For each, say whether the artifacts support it exactly, approximately, or not at all.

Write `oracle-blindness/docs/BENCHMARK_AUDIT_REPORT.md`. Order findings by severity: (1) pairs that must be removed, with ids and why; (2) rules that are wrong, with the counterexample; (3) labels that are wrong; (4) exclusions that were wrong; (5) weaknesses that must be stated as limitations; (6) things that checked out, with the count checked.
