# The agent-evaluation sample, and why it is not cherry-picked

The agent run is on 100 of the 330 pairs, because a frontier model on all 330
costs more than the project's budget. A subset invites one obvious objection —
*you chose the pairs that suit you* — so the draw is defined by stated criteria
rather than by a random seed, and this document is the audit trail.

## The draw

Stratified proportionally on the two dimensions the paper reports, tier and
release subset (largest-remainder allocation), with two caps applied inside
the strata and a distribution match on the third dimension:

- **at most 4 pairs from any one repository.** The pool is concentrated: one
  repository (`swirlai_swirl-search`) supplies 39 of 330 pairs, so a
  proportional sample would give it 12 of 100 and let a reader attribute the
  agent result to that project. The cap binds it to 3.
- **at most 4 pairs for any one dependency.** `numpy` appears 14 times,
  `requests` 11. Without the cap a few libraries would dominate.
- **footprint bands matched to each stratum's distribution** (0, 1, 2, 3–4,
  5–9, 10+ files touched), not merely its median. The file count has a long
  tail (0 to 88) and a median match hides the shape, which is exactly where
  "you picked the small ones" would live.

Two things are deliberately **not** preferences:

- **Trace availability.** Preferring pairs the behavioural gate can grade
  would make the sample easier to *grade* than the pool it stands for, and the
  pass rate would then be reported on a subset selected for the grader's
  convenience. Coverage is reported instead (26% of the sample, 25% of the
  pool).
- **Small footprints.** See the band match above.

## The result: the sample is determined, not sampled

Run with seeds 1, 7, 20261009 and 99999, the draw returns **the same 100 pairs
every time** — the constraints are tight enough to determine it. There is no
seed to have chosen favourably, and the sample can be regenerated by anyone
from the pool file:

```
python3 scripts/gh/sample_agent.py --n 100 --out pilot/agent_sample_100.jsonl
```

## Marginals, sample against pool

| | pool | sample |
|---|---|---|
| strong tier | 59.4% | 60.0% |
| medium | 12.4% | 12.0% |
| hard | 19.7% | 19.0% |
| indirect | 8.5% | 9.0% |
| regular subset | 48.8% | 49.0% |
| large subset | 51.2% | 51.0% |
| test-reachable | 85.8% | 83.0% |
| footprint 0 files | 8.5% | 9.0% |
| footprint 1 | 40.6% | 41.0% |
| footprint 2 | 18.8% | 19.0% |
| footprint 3–4 | 12.4% | 12.0% |
| footprint 5–9 | 10.0% | 9.0% |
| footprint 10+ | 9.7% | 10.0% |
| has a reference trace | 25% | 26% |

Every marginal is within one point of the pool. Coverage: **71 of the 73
repositories** and 93 distinct dependencies appear; the most any single
repository contributes is 3 pairs and the most any dependency 3.

## What this does not claim

The sample represents the pool on the dimensions above. It cannot represent
dimensions nobody measured — if removal difficulty depends on something
orthogonal to tier, subset and footprint, the sample is balanced on the wrong
axes and the pass rate transfers less well than the marginals suggest. The
pool itself is 73 repositories of open-source Python with passing CI, which
is the population the paper claims and no more.
